# code-review 不足记录（MR238 实测，2026-11-11）

本文件是 **0.3.0 之后**的问题清单，来源：用插件审查流水线对 wisdom-financial-credit-platform-web MR 238
最终 diff（245 文件，代码 diff 909,626 字节）做了一次离线全量审查，并与团队 GitLab AI Code Review bot
的 6 轮结果、2 条人工审查意见做对照。记录事实与差距，解决方案见后续 v0.4 设计文档。

## 1. 实测条件与边界（结论可信度）

| 事实 | 影响 |
| --- | --- |
| 离线模拟，未走真实插件链路：没有 reviewer preset（无只读工具面/guard/人格）、没有 `structured_output` 工具，审查者只能看 prompt 文本、输出 JSON 后补校验 | 涉及"调用点/缺失/不存在"的结论无法 grep 自证；Suspense 误报有一部分是测试方法造成的 |
| 为覆盖全量把 `maxDiffBytes` 从 200KB 提到 1,000,000 | 默认配置只覆盖该 MR 的 ~22%（909KB），这次结果不代表默认行为 |
| 单次采样，无复验、无重复跑 | 无法估计稳定性/召回率；bot 是 6 agent + 复验 |
| 未执行"按 finding 自动修复"闭环 | 只验证了"发现"，没验证"修得对不对/安不安全" |

## 2. 测试结果对照

- 输出 6 条 finding，校验层 0 丢弃：3 条站得住（回显解析失败静默丢弃→替换提交删数据、文件 629 行、死引用），
  1 条已知人工 wontfix（BEH-001 纯数字静默），2 条存疑（Suspense 兼容别名"无调用点"属推断；MNT-016 大括号比团队规范严）。
- bot 末轮 1 条 low（批量删除 ids 无分批）我们没报；bot 报过的 setZoom 回归/undefined/重复向量等中间态问题
  在最终 diff 里已修复，我们不报是正确的；文件超长与 bot 一致。
- 结论：**actionable 精度 3/6（50%）**，2 条 medium 中 1 条是误报；漏报 1 条 low。

## 3. 不足清单

### P0：能力缺口

| # | 不足 | 证据 | 影响 |
| --- | --- | --- | --- |
| P0-1 | **没有 MR/任意 diff 审查入口**：只审"当前 turn 的 workspace diff"与"链内触达文件的当前内容"，无法审 `base..head` 这种提交范围 | 本次必须先手写 `/tmp/cr-mr238/build.mjs` 跑流水线 | 团队主场景（MR）用不上，只能靠人工搬运 |
| P0-2 | **大 diff 容量不成立**：单 agent 单次 910KB≈25 万 token、约 9 分钟，接近/超过 `asyncReviewerTimeoutMs` 默认 10 分钟；无 token 预算、无分块、无并行、无降级 | 本次运行耗时与 prompt 983,782 字节 | 大 MR 要么超时要么截断，实际"审不完" |

### P1：质量与口径缺口

| # | 不足 | 证据 | 影响 |
| --- | --- | --- | --- |
| P1-1 | **证据约束只在 prompt 里，没有机械化**：REVIEW_SCHEMA 没有 `sourceSnippet` 字段，校验层不验证片段是否真实存在于 diff/文件；"某调用点/某逻辑不存在"不要求 grep 证据；medium+ 无独立复验 | Suspense finding 纯推断；prompt 里"逐字反引号片段"无校验 | 误报会变成主 agent 的修复指令，浪费轮次、可能改错 |
| P1-2 | **规则口径与团队规范不一致**：MNT-016 严于团队 CR-006.05（"单行语句可例外"）；严重度映射没有团队"阻塞分类"（logic/permission/security/data/exception/concurrency）；团队非阻塞建议会被我们当 medium 触发自动修复 | MNT-016 误报；MNT-011（629 行）在团队侧被 waived | 与团队门禁打架，产生无效修复轮 |
| P1-3 | **没有修复策略（Fix Policy）**：团队规范有 `auto_safe / manual_only / forbidden`，生成代码/契约/权限/资金类禁止自动修复；我们对所有 finding 一视同仁地回灌 | 本次若真触发修复，Suspense 建议会去改 kubb 生成代码 | 高风险误修，可能破坏生成链路/契约 |
| P1-4 | **没有人工决策记忆**：`#ai-wontfix`（BEH-001 纯数字静默）与 `#ai-waive`（580 行拆分）无法被感知，跨轮/跨次重复报 | 本次离线复核再次报出 BEH-001 | 已裁决问题反复打扰，信噪比下降 |

### P2：工程与演进缺口

| # | 不足 | 证据 | 影响 |
| --- | --- | --- | --- |
| P2-1 | **规则库缺口**：没有"解析/读取失败不得在替换语义下静默丢弃"的数据完整性硬规则（本次靠 PRINCIPLE-correctness 兜住）；没有"批量参数随数据量增长必须分批/限流"（漏了 bot 唯一未处理项）；无生成代码（kubb）专门口径 | 回显 findings 归属 PRINCIPLE 而非规则；漏批量删除 | 发现依赖原则运气的成分高；生成代码产生噪声 |
| P2-2 | **没有质量回归语料**：248 个测试只验证机制（prompt 结构/校验/渲染/状态机），没有一条验证"审得准不准" | 本次只能手工对 bot/人工结论做对照 | 改 prompt/规则无法量化，靠单次手感 |
| P2-3 | **输出不可审计**：finding 无 FID/证据片段/复验状态/门禁分类；无跨轮"已报未修"追踪 | 对比 bot 的 FID、source_snippet、复验次数 | 人工 triage 与责任追踪弱 |
| P2-4 | **预算/超时不随规模自适应**：`maxDiffBytes`、`asyncReviewerTimeoutMs` 固定；全量模式读文件无 token 上限；journal 依赖 storageDomain（缺失时仅内存），无跨重启去重 | 本次需手动调大预算；重启即丢历史 | 大仓库/长链下行为不可控，记忆易丢 |
| P2-5 | 生成代码/批量重生成变更的噪声：本次 124 个 Suspense 文件、kubb 生成物占据大量审查预算 | 审查者把注意力耗在生成代码语义上 | 有效代码覆盖被稀释 |

## 4. 本次做到 / 没做到的（基线）

- 做到：数据删除风险（echo 回显）、死代码、文件超长；与 bot 一致的不重复报；规则作用域生效；校验层 0 丢弃。
