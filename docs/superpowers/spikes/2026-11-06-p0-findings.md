## Spike A — 右栏 tab 占座

### 结论

- **bundle 安装与激活成功**：`plugin_manager(install_bundle, target:/Users/liyu/Documents/www/DeepSeek/deepseek-harness/deepseek-harness-plugin/bug-workflow)` 返回 `application: applied`、`warnings: []`；profile 中生成 link 依赖并列入 `dsh.profile.bundles`；host 插件行 `include:bug-workflow` 处于 active（无 `Config`，故 `status: "absent"`，与 `index.js` 只导出空 `apply` 一致）。
- **client 注册代码按 0.2.2 实际契约实现**：`ctx.sidebarRightTabs.register(definition)` 注册 tab 类型（`id = @liyuera/dsh-bug-workflow`，`kind = bug-board`），`ctx.slots.inject('sidebar.right.pane.tab', () => ctx.slots.register({ name, key }, BoardTab))` 注册 body，key 等于 definition 的 `id`。
- **brief 预期代码有一处契约差异**：`guide` 不是 `{ order, title }` 对象，而是 **guide entry 数组**（每项 `{ id, order, title, description?, icon? }`）。0.2.2 的 `register()` 会执行 `const entries = definition.guide ?? []` 后立刻 `entries.map(...)`；若按 brief 预期写对象，注册时抛 `entries.map is not a function`。本次已按实际契约写成数组，其余字段（`id`/`kind`/`title`/`multiple`）与 brief 一致。
- **是否成功占座**：✅ 已由 controller 在 live client 上确认——`cordis_inspect_query(platform:'client', provider:'Slots', method:'listSubTree', input:{root:'sidebar.right.pane.tab'})` 返回的 occupants 中包含 `@liyuera/dsh-bug-workflow`（registrant `tk`，`active: true`），说明 `bug-workflow/client.js` 已在页面执行且 slot body 注册成功。guide 入口的目视效果留给用户最终验收确认。

## Spike B — 平台取数

> 验证环境：用户 Chrome 中已登录的 `https://ecard.htwisdom.cn/HT_TEAM/project/…/issues?issueCode=YGFNXDJRFWDJSYJJYY-647`（tabId `1178530378`）。
> 方法：所有请求都由 `chrome_eval` 在该页面的同源上下文里发出（同步 XHR / `fetch`），token 在表达式内部从 `localStorage['app/access-token']` 读取，**从未打印、落盘或提交**；返回内容只保留 HTTP 状态码、JSON 字段名、条目计数与结构。全程只发 GET，未写任何数据，未导航/点击用户页面。

### 结论

- **鉴权只需一个请求头**：`Htwisdom-Auth: <token>`。token 取自 localStorage 的 `app/access-token`（纯字符串、不是 JWT）。实测不依赖 Cookie：页面内 `fetch('/api/htwisdom-system/user-auth-info', { credentials: 'omit', headers: { 'Htwisdom-Auth': token } })` 仍返回 HTTP 200 / `code: 200`，所以 Node 脚本只带 token 即可。**未观察到需要 `Authorization: Basic`**：`GET /api/htwisdom-system/app` 返回 17 条应用配置，字段只有 `credentials: boolean`（`id/name/code/appUrl/appType/enable/component/image…`），没有 clientId/clientSecret。
- **当前用户身份**：`GET /api/htwisdom-system/user-auth-info` → `data.user.id` 就是「负责人 = 我」过滤要用的 id（任务记录里对应字段是 `refHandlePersonId`，两者值域相同）。
- **工单详情**：`GET /api/htwisdom-team/task/detailByTaskCode/<taskCode>` 返回 45 字段，type/status/priority/version/assignee/participant/milestone/children 全都有；**附件不在详情响应里**，需要另调 `POST /htwisdom-team/file/list`。
- **字典**：`GET /api/htwisdom-system/dict/business/dictionary?codes=a,b` **必须带 `codes`**（不传或传错参数名 → HTTP 400「字典编码不可为空」）。`data` 是「字典编码 → 条目数组」的对象；条目中 `dictKey` 是过滤值（如 `001_CREATE`），`dictValue` 是显示名，`color` 可直接用于 UI。实测 `teamTaskStatus` 6 条、`teamTaskType` 7 条、`teamTaskPriority` 4 条。
- **评论**：`GET /api/htwisdom-team/remark/list?refTaskCode=<code>&remarkType=001_TASK` 返回数组；647 为 0 条，抽查前 5 条工单各 1–2 条。条目 16 字段，`content` 是 `encodeURIComponent` 过的文本，另有 `createdUserName`、`remarkType`、`remarkStatus`。
- **「我的工单」列表接口：已找到，不需要降级为手动按编号添加。** `GET /api/htwisdom-team/task?current=1&size=N&refHandlerPersonId=<user.id>` 返回 MyBatis 分页对象 `{records,total,size,current,orders,…}`，当前用户名下 **258** 条；支持 `taskStatusList` 多值（3 个状态 → 258 降到 2）、`createdUserId`（我创建的 20 条）、`refProjectId`（项目内 196 条）、`keyword`+`keywordType=taskCode` 精确搜编号（1 条）、`descs=createdTime` 排序。列表记录 48 字段，已包含 `taskTypeName/taskStatusName/taskPriorityName/refHandlePersonName/refProjectName/refVersionUnitName`，渲染卡片不需要再调详情。
- **树接口存在但不必用**：平台项目页用的是 `GET /api/htwisdom-team/task/tree`（与 `/task/taskCount` 并行请求）；**缺 `descs` 排序参数时实测 500「服务器异常」**（只带 `keywordType` 仍 500；带 `descs` 不带 `keywordType` 为 200），带页面同款参数则 200 返回节点数组（节点含 `children`）。插件选扁平分页 `/task` 更合适。
- **附件**：`POST /api/htwisdom-team/file/list`，body `{ refBusinessIdList: [taskId] }`（代码级确认）；该路径 GET 返回 405。只读约束下未调用。
- **状态写回**：`POST /api/htwisdom-team/task/update`，payload `{ id, columnUpdateDTOList: [{ fieldName, fieldValue }] }`；仅做代码级确认，**没有发出任何写请求**。
- **登录自动化**：`POST /htwisdom-auth/oauth/token` 的 `password` 由前端 RSA（JSEncrypt）加密，公钥来源仍未确认；P0 继续用「token 粘贴」，P1 再在原生 HTTP 登录 / 页面驱动登录中选择。

## Spike C — GitLab + AI Review 解析

> 验证环境：用户 Chrome 中已登录的 GitLab MR 页面（tabId `1178530379`，`https://git.htwisdom.cn/wisdom-financial-service-platform/wisdom-financial-credit-platform-web/-/merge_requests/223`，页面状态 `merged`）。
> 方法：notes 由 `chrome_eval` 在该页面的同源上下文里用同步 XHR 读取（依赖页面登录态，**没有读取/打印/落盘任何 Cookie 或 token**）；只记录 HTTP 状态码、响应头、字段名与解析结果。真实 note body 仅通过本机 loopback 临时收集器交给 Node 解析器跑一遍，收集器与临时文件均已删除；提交仓库的是去敏后的 fixtures。全程只发 GET。

### 结论

- **notes API 可用（页面上下文）**：`GET .../merge_requests/223/notes?sort=desc&per_page=100` 返回 HTTP 200，`x-total: 11`、`x-page: 1`、`x-per-page: 100`、`x-total-pages: 1`。11 条 note = 7 条 user note + 4 条 system note；note 字段共 14 个：`id, body, author, created_at, updated_at, system, type, noteable_id, noteable_iid, noteable_type, resolvable, confidential, commands_changes, attachment`。`body` 是原始 Markdown，可直接交给解析器。
- **3 条 AI Review note（含人工复核）**：#72348 是 `AI Code Review (...)`（`结论: 需要修改`）；#72351 是 `AI Code Review (...)`（`结论: 可直接合并` + 1 条历史未收敛）；#72354 是 `AI Code Review 人工复核结果`（`结论: 可直接合并`、`剩余问题: 0 条`）。按 `created_at` 最新一条是 #72354（人工复核）。
- **解析器在真实 note 上判定正确**：
  - #72348 → `verdict: changes`，blocking 1、nonBlocking 2；阻塞项级别=中、门禁分类=逻辑错误，两条非阻塞项均为级别=低 / 门禁分类=非阻塞建议。
  - #72351 → `verdict: pass`，blocking 0、nonBlocking 1（历史未收敛，级别=低 / 门禁分类=非阻塞建议）。
  - #72354 → `verdict: pass`，blocking 0、nonBlocking 0；它没有条目列表，模板里显式的 `剩余问题: 0 条` 是唯一的零问题证据。
  - 其余 8 条 note（system note、`Sensitive Content Gate`、waive 指令等）→ `unknown`。其中一条 `Sensitive Content Gate` 也含 `结论:` 但没有 `AI Code Review` 标记，说明「先按 AI 标记过滤」是必要规则。
- **隐藏统计段已隔离**：真实 note 的 `> 备注：以下隐藏数据仅用于统计…` 之后是 `<!-- AI_REVIEW_FINDINGS {...} -->` JSON。解析器截掉整行标记（含 `> ` 前缀，避免污染最后一条字段），并额外剥掉 `AI_REVIEW_*` HTML 注释；对真实解析结果做泄漏检查，issue 字段中 `AI_REVIEW`、`finding_id`、`source_snippet`、`备注：以下隐藏数据`、行尾 `>` 均为 `false`，字段首尾空白也已清理。
- **格式骨架已确认**（fixtures 按此去敏）：`## AI Code Review (...)` / `结论: **需要修改|可直接合并**` / `摘要: …` / `模型: …` / `Diff 规模: …` / `风险等级: **正常**` / `历史未收敛: \`N\` 条` / `### 需要关注的问题` 或 `### 历史未收敛问题` / 编号条目 `1. **文件**: \`src/...\`` + 缩进字段 `- FID:`、`- 级别:`、`- 门禁分类:`、`- 位置:`、`- 问题:`、`- 建议:`。字段值允许 Markdown 加粗/反引号；条目里另有 `复验次数/类型/提交人/源码/状态` 等可忽略字段。
- **解析失败策略（不猜）**：`需要修改` 但解析不到条目、条目缺少 `文件` 或 `问题`、`可直接合并` 但无条目且无显式 `0` 条声明 → `unknown`。`可直接合并` + 无条目 + 显式 `剩余问题: 0 条`（人工复核 note）→ `pass`；这是 brief「有结论但没有条目 → unknown」的细化：显式 0 条是模板数据，不是猜测，否则最新的人工复核会被误判为 blocked。
- **fixtures + 自测通过**：`review-needs-fix.md` → `changes` / blocking 1 / nonBlocking 1；`review-pass.md` → `pass` / blocking 0 / nonBlocking 1；另 9 个边界用例全 PASS，`node bug-workflow/scripts/review-parser.mjs` 退出码 0。
- **`probe-gitlab.mjs` 的真实 token live 运行未执行**（用户不在场、token 未提供）。用占位 token 实测 Node 进程可访问 `https://git.htwisdom.cn`，notes 请求返回 HTTP 401（token 无效），说明 Node 侧 TLS/网关/`PRIVATE-TOKEN` 请求路径可达；本地 mock 的成功路径（200 → 过滤 → 倒序取最新 → 解析 → 退出 0）也已跑通，但两者都不是有效 token 的 live 数据验证。

### 结论

- **host half 能启动子代理并让它改到 worktree：✅ live 已验证。** `GET /bug-workflow/spike/subagent` → HTTP 200，body 里 `ok:true`、`stopReason:"completed"`、`childId=99637234-970b-4d46-81bc-ce7fc278fab6`、`messageId=61f9df55-197b-4ffa-9af0-d5bea2d3075f`；worktree `bug-workflow/.tmp/worktree/hello.txt` 由 `hello` 改成 `hello p0`，`git status --porcelain` = `" M hello.txt"`，路由返回 `files:[{status:"M",path:"hello.txt"}]`，`git diff` 只有这一行。子代理自报 `pwd` = 该 worktree，未执行 commit。（该 spike 路由已在 `7195b95` 删除，以上为历史证据。）
- **`startActivation` live 契约（0.2.2-rc.1）**：

  ```ts
  interface SubagentActivationSpec {
    readonly provider: string
    readonly label: string
    readonly childId?: SessionId          // 预留本地身份；省略时由 manager 分配
    readonly request: Omit<SubagentStartRequest, 'label' | 'signal'>
    readonly signal: AbortSignal          // 必填；只取消「发布前」的创建
    readonly delivery: 'parent' | 'caller'
  }
  interface SubagentStartRequest {
    readonly cwd?: string                 // 相对路径按父 Agent 当前目录解析；省略则继承
    readonly agentPreset?: string         // 只有 spawn 支持独立 preset
    readonly prompt: ContentBlock[]       // 注意：ContentBlock[]，不是字符串
    readonly parent: Agent                // 必须是 live Agent
    readonly agentOptions?: AgentOptions
    readonly outputSchema?: ObjectJsonSchema
    readonly maxDepth?: number
  }
  // 返回：{ childId, messageId?, result: Promise<SubagentResult>, dispose() }
  // SubagentResult = { output: ContentBlock[], structured?, diagnostic?, stopReason }
  // stopReason: 'completed' | 'aborted' | 'error' | 'max-tokens' | 'refusal'
  ```

  本地子代理（`spawn`/`fork`）的 `messageId` 一定存在，可后续续聊/冷恢复；`provider:'spawn'` 是 `@deepseek-ai/dsh-subagent-spawn-in-process` 的默认注册名（`providerName=spawn`）。`delivery:'caller'` 不产生父会话的完成通知，由调用方 await `result`；`delivery:'parent'` 才写通知（且要求 Session persistence）。
- **父 Agent 获取方式：`ctx.agents.roots()[last]`，没有创建 disposable worker。** live `agents` 服务提供 `get(id)` / `list()` / `roots()` / `isOwnedBy(id, owner)` / `create()` / `resume()`（`currentInitiator()` 也存在）。`agent/created` 是 serial 事件，payload 为 `{ agent, source: 'startup'|'resume'|'clear'|'compact', signal? }`，只在**创建时**触发；当前控制器会话的 Agent 早于插件加载，所以监听器只能当兜底，不能作为主路径。路由默认取「最近注册的 live root」，也支持 `?parent=<sessionId>` 用 `agents.get()` 锁定。实测 `liveAgents:{total:2,roots:1}`，parent = `session-3f476be9-cfd2-4ced-8ed3-277ee9659713`（控制器会话；另一个 live agent 是本次实现者子会话）。没有调用 `ctx.agents.create()`，所以也没有需要 dispose 的 disposable worker 会话。
- **`request.cwd` 的作用位置**：它把子代理的**工作目录**设为 worktree（子会话 projection `workingDirectory` = `.../bug-workflow/.tmp/worktree`，子代理自报 `pwd` 相同，且用相对路径 `hello.txt` 改文件成功）；但持久化 Session header 的 `cwd` 仍是继承的 workspace 根（`.../deepseek-harness-plugin`）。P1 判断/展示「子代理在哪个 worktree」时不能读 `session.header.cwd`，要读 `workingDirectory` projection（本会话里 `forgeWorktree.cwd` 也是该路径）。
- **插件重载：不需要重启 app，但同路径重装无效，必须 remove → install。** 同路径 `install_bundle` 返回 `application:"failed", changed:false, error:{code:"already-installed"}`；把 `package.json` 版本从 0.0.1 bump 到 0.0.2 后重装仍是 `already-installed`（`link:` 依赖的身份是路径，不是版本）。`remove_bundle('@liyuera/dsh-bug-workflow')` → `install_bundle(<abs path>)` 返回 `application:"applied", changed:true`，新 host 代码立即生效（路由 405 探针 + 成功 GET 双重确认），全程未重启 DSH。验证后版本号已回退到 0.0.1。
- **子代理生命周期/副作用**：`result` 在 teardown 后 settle，正常完成不需要 `dispose()`；spawn 结束后 live agent 数仍为 2（parent + 实现者），没有常驻 Activation 占槽。三次验证运行各持久化了一个子会话（`01095901-…`、`6380c983-…`、`99637234-…`），header 为 `origin:"subagent"`、`parentSession:"session-3f476be9-…"`、`delegationDepth:1`、`agentPreset:"cordis"`（继承父会话当前 preset revision），并在父会话日志各追加一条 `subagent/catalog`（`mode:"continuable", label:"p0-spike"`）。这些子会话是**持久化且可见的**，本任务未删除；P1 不能假设子会话会自动消失。

### 后续动作

- **P1 直接复用调用形状**：`ctx.subagents.startActivation({ provider:'spawn', label, delivery:'caller', signal: AbortSignal.timeout(…), request:{ prompt:[{type:'text',text}], parent, cwd:<绝对 worktree 路径> } })`；脚本/工作流用 `caller` + `await activation.result`，不污染父会话上下文。若需要父会话里的完成通知，改 `delivery:'parent'` 并确认 persistence 可用。

## Spike E — storageDomain 持久化

> 验证环境：live DSH 0.2.2-rc.1 desktop profile（Web GUI `http://127.0.0.1:49254`；`lsof -nP -iTCP -sTCP:LISTEN` 确认 `DeepSeek` pid 882 监听该端口），插件 `@liyuera/dsh-bug-workflow` v0.0.1。全程**未重启 app**、未新建/删除用户会话、未手写 profile 文件；host-half 重载只用 `plugin_manager` 的 `remove_bundle` → `install_bundle`。
> 说明：本节的路由命令与输出均为 `7195b95` 清理前的历史证据；`/bug-workflow/spike/state` 路由与 `~/.dsh/storages/bug_workflow_spike.json` 已在该 commit 随 P0 收尾删除（见文末「P0 收尾」），当前无法按原命令复现。

### 结论

- **storageDomain 跨 host-half 重载持久化：✅ live 已验证。** 实测序列：写入 `{id:'spike',at:1793981813495,value:'task-5-before-reload'}` 后，重载 #1–#2 的 `read` 都返回 `at=1793981813495`；随后再写 `at=1793981832430`，重载 #3–#4 读回该值；最后写 `at=1793981915605`，重载 #5 读回该值。共 **5 轮** `remove_bundle` → `install_bundle`（每次 host half 重新 `apply`），每次读到的都是最近一次写入的值，而不是最初的值。重载 #4/#5 读取的 `domainOpenedAt` 分别为 `1793981914168` 与 `1793981919258`（不同），证明读到的值来自**重新 open 的 domain（磁盘加载）**，不是旧 fiber 的内存残留。持久化文件是 `~/.dsh/storages/bug_workflow_spike.json`（7195b95 清理时已删除）。
- **域名必须匹配 `UNIT_NAME_RE = /^[a-z][a-z0-9_]*$/`；brief 示例 `bug-workflow-spike` 非法**（连字符不被接受，`defineDomain` 在模块加载时直接 throw）。本 spike 实际使用 **`bug_workflow_spike`**：`version: 1`、表 `state`、记录 key `spike`、默认 `single` 布局（`layout` 省略，json backend 默认 single）。
- **实际使用的 0.2.2-rc.1 契约**（来源：`cordis_inspect_query(platform:'host', provider:'Service', method:'listService', input:{service:'storageDomain'})` + app.asar 内 `@deepseek-ai/dsh-storage-domain/README.md` 与 `lib/index.js`）：

  ```ts
  // @deepseek-ai/dsh-storage-domain 导出
  defineDomain<S extends DomainSpec>(spec: S): S   // 校验 name/version/layout/invalidRecords/表名
  domainTable<V>(schema: ZodType<V>): DomainTableSpec<string, V>   // => { valueSchema: schema }

  interface DomainSpec {
    name: string                          // UNIT_NAME_RE: /^[a-z][a-z0-9_]*$/
    version: number                       // 非负整数；旧版本要靠 compatibleVersions 才能 open
    layout?: 'single' | 'per-record'      // 省略 = 后端默认布局（json = single）
    compatibleVersions?: readonly number[]
    invalidRecords?: 'backup-and-skip'
    global?: { schema: ZodType<G>; initial: G }   // schema 不能接受 null（null 是“从未写入”哨兵）
    tables: Record<string, { valueSchema: ZodType<V> }>
  }

  // ctx.storageDomain（facility）
  open<S extends DomainSpec>(spec: S): Promise<Domain<S>>   // 名字已打开/仍在关闭 => DomainError code 'already-open'
  get(name: string): DomainImpl | undefined                 // 诊断用
  closeAll(): Promise<void>                                 // facility 卸载兜底

  interface Domain<S extends DomainSpec> {
    readonly name: string
    table<N extends keyof S['tables'] & string>(name: N): KvTable<TableKeyOf<S, N>, TableValueOf<S, N>>
    close(): Promise<void>             // 幂等；handle 归调用方所有
  }

  interface KvTable<K extends string, V> {
    get(key: K): V | undefined        // 同步，从内存读
    put(key: K, value: V): Promise<void>   // backend 持久化完成后才 resolve；源码级：不校验写入值
    entries(): IterableIterator<[K, V]>
    keys(): IterableIterator<K>
    readonly size: number
    delete(key: K): Promise<boolean>
    update(key: K, fn: (current: V) => V): Promise<V>
  }
  ```

  `open` 的校验/失败链（每步都失败整个调用）：`already-open` → backend 路由（`backend-not-found`）→ 要求 `kv` facet（`facet-unsupported`）→ `loadAll` 并按表 schema 校验每条记录（`invalid-record`，带 table/key）→ 构造 handle。`domain/changed` 是 **in-process** 事件，写入已持久化后才按顺序 emit；本 profile 的 backend 是 `json`（`storage-json.root = dshHomePath('storages')`，`storage-domain.backend = json`），domain 文件即 `$DSH_HOME/storages/<name>.json`。
- **打开/关闭位置**：在 `apply(ctx)` 内用 `ctx.inject(['storageDomain'], cb)` 打开（不改 `export const inject = ['webServer']`，所以无 storage 的 profile 里 Task 4 路由仍能加载）；`storageCtx.effect(() => async () => { const domain = await pending; await domain.close(); })` 作为 disposer：先 await open 再 close，因此“open 晚于 dispose”也会被关闭；`Domain.close()` 幂等，facility 卸载时还有 `closeAll()` 兜底。路由 `GET /bug-workflow/spike/state?action=write|read`（已在 `7195b95` 删除）注册在插件根 context 上，而打开/关闭 domain 的这个 disposer 挂在 `ctx.inject(['storageDomain'], …)` 的子 fiber 上；插件卸载时根 context 与子 fiber 一并 dispose，路由与 disposer 同时消失。
- **卸载时 close 确实发生**：`storage-domain` facility 是独立插件，不随本 bundle 重载；如果旧 fiber 没有 close，facility 的 `reserved` 会一直占用 `bug_workflow_spike`，新 fiber 的 `open` 会在 20×100ms 重试后以 `already-open` 失败、路由 500。实测每次重载后 `read` 都立即 200 且 `specSource` 已解析 → 名字已释放、disposer 生效。
- **`already-open` 竞态必须重试**：dev-dock 的既有实现用 10×100ms 重试同一竞态；本 spike 用 20×100ms（`OPEN_ATTEMPTS=20`, `OPEN_RETRY_MS=100`），本次重载间隔足够、未真正触发重试，但 P1 必须保留重试，否则连续热重载会偶发 500。
- **宿主包导入方式（重要）**：本 bundle 是 `link:` 目录且没有自己的 `node_modules`；从真实路径 `import '@deepseek-ai/dsh-storage-domain'` 在 Node 24 下 **`ERR_MODULE_NOT_FOUND`**（实测）。spike 运行时优先用 Electron `process.resourcesPath` 拼出 `app.asar/dsh/node_modules/@deepseek-ai/dsh-storage-domain/lib/index.js` 并 `await import()`（成功；响应里 `specSource` 原文），再回退 bare specifier / 内联 spec。**P1 不应保留 app.asar 硬编码**：应像 `dev-dock` 一样 bundle 依赖，或声明 peer 并安装。
- **schema 责任**：`open` 会 `valueSchema.parse(raw)` 校验存量记录；`put` 在 0.2.2 源码里不校验写入值。本 spike 为不引入 zod 使用 `{ parse() }` 形状的最小校验器（校验 `id`/`at`/`value` 三字段）；P1 必须换成真 zod schema，并按数据重要性考虑 `invalidRecords: 'backup-and-skip'`（需要 backend 提供 `backupRecord`）或直接 fail-loud。
- **落盘格式**（json backend + single layout）：`~/.dsh/storages/bug_workflow_spike.json`，mode `0600`：

  ```json
  {
    "unit": { "name": "bug_workflow_spike", "version": 1 },
    "global": null,
    "tables": {
      "state": {
        "spike": { "id": "spike", "at": 1793981813495, "value": "task-5-before-reload" }
      }
    }
  }
  ```

  `read` 不重写文件（写后 mtime 到读后不变：`1793981813` → 同值）；写入是临时文件 + fsync + 原子 rename + 父目录 fsync。
