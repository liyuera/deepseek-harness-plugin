### 3.2 边界/鲁棒性逐步观察

| 用例 | 观察 |

### 3.3 E2E 的隔离与可重复性

- 每个场景独立的 `mkdtemp` 目录（`dsh-bw-e2e-*`）：`repo` + `origin.git`（bare）+ `.dsh-worktrees/<code>`；运行后 `rmSync`，两轮后 `/tmp` 无残留。
- mock GitLab 以 `127.0.0.1:0` 监听随机端口，token 校验；`closeAllConnections()` + `close()` 清理。
- lint/test 用 fake `execCommand`（记录 command/cwd/timeout），不执行 npm/全局命令；Review-fix runner 是 fake（只改 worktree 并返回真实结果形状），host 的 commit/push 是真 git。
- 只使用 `node` 与 `git` 二进制；不访问网络、不读取真实仓库/凭据/工单。

1. **真实 GitLab**：保存真实 token（`POST /api/gitlab-token`）→ 真实 `gitlabBaseUrl`（TLS/网关/WAF）→ 在真实业务仓库的个人分支/worktree 上执行 `/api/deliver` → 确认 push、MR 创建/复用、标题/目标分支/description、`remove_source_branch:false`、无 reviewer；真实 GitLab API 与 P0 契约的差异以这次为准。
2. **真实业务仓库与真实人工测试**：E2E 用临时仓库；live 648 的 plan/修复在插件仓库上。真实业务仓库的 lint/test 命令、依赖、目标集成分支是否存在、真实人工测试与合并均未执行。
3. **真实 AI Review 子代理**：E2E 的 Review-fix runner 是 fake；真实 `runReviewFix` 的模型质量、耗时、写范围与 prompt 约束未 live 验证（P3/P4 的真子代理经验只覆盖分析/修复）。
4. **GUI 视觉/交互/刷新**：GitLab 设置/token 卡、`submitting` 提交按钮、MR/Review 合并面板、错误 banner、窄栏/主题/读屏均未目视；client 更新后**必须刷新页面**。
5. **真实人工合并与归档**：E2E 用 mock MR 状态；真实 GitLab 合并由人完成，插件只轮询 `state=merged` 并本地 `dismiss`。未验证真实合并后的 `merged → done` 出看板。
6. **平台状态写回**：`writebackStatus` 仍未实现（P6）。
7. **Windows / 多 host / 多工单并行 / app 整体重启**：只在 macOS + 单 host 进程验证；delivery 的默认 lint/test 执行器依赖 `/bin/sh`，Windows 当前不支持。
8. **notes 分页与 closed MR**：只请求 `per_page=100`，无翻页；MR 被人工 close 没有专门处理（见 §8）。

## 8. 残余风险（不阻塞 P5 验收）

| # | 风险 | 影响/处置 |
| --- | --- | --- |
| N2 | claim-before-transition：`review.last-note` 已写、`review_requests_changes` 未写时进程崩溃 | 该 note 永久去重（skip，不重复）。fail-safe 方向；P6 可加 pending-round claim + `mr_open` 对账 |
| N3 | `review.fix-commit` 写/清是 best-effort | 残留记录由下一轮 purge + `round/noteId` 绑定兜底；极端情况下需要重跑 child |

| — | notes 固定 `per_page=100`，无分页 | 评论 >100 条时更早的 AI note 可能被漏掉；当前只处理最新一条，影响有限 |
| — | closed MR 未处理 | 服务只识别 `merged`；人工 close 的 MR 仍可能被当 `mr_open` 轮询，需人工处理（P6） |

## 9. P6 backlog

1. **平台状态写回**：`writebackStatus` 打开时向星瞰河山平台写「进行中 / 已修复」（delivery 开始 / `done` 或 MR merged 后），包含失败静态化与重试。
2. **Review 修复轮 lint/test**：在 review-service 的宿主 commit 前复用 delivery 的 `execCommand` 门禁（失败 block，不 commit/push）。
3. **MR discussions 端点**：把 Review 的阻塞项以 discussion 形式回写/跟踪（当前只读 notes；不 resolve/close）。
4. **closed MR 处理**：MR `state=closed` 时 block（如 `review-mr-closed`）并提示人工重开/重新交付，避免继续轮询。
5. **notes 分页**：`listNotes` 支持 `page` 或 `per_page` 翻页（至少覆盖 >100 条评论），并保留去重。
6. **客户端行为测试与 GUI 截图**：提交 DOM/渲染测试（delivery/review 面板、错误命名空间、token 卡片、计时/读屏），补 GUI 截图作为验收留证。
7. **快照裁剪/归档**：`fixes`/`reviewRounds` detail 端点或归档，避免 snapshot 无界增长。
8. **Windows 支持**：为 delivery 的 lint/test 提供跨平台执行器（或明确 Windows 不支持并文档化）。
9. **真实联调脚本/验收记录**：真实 GitLab sandbox、真实业务仓库、真实 review bot、真实人工合并的验收记录。

## 10. 结论与关注点

- P5 的交付主链、Review 轮询/修复/合并归档以及评审要求的边界场景，在**隔离 E2E**（28 条断言、两次运行）与 **564 例单测**中均有可重复证据；live 只读验收确认 host 半边、snapshot 形状、路由错误路径与热重载正常，且没有写真实数据。
- 最大的未验证面仍是**真实 GitLab 与真实业务仓库/GUI**：mock 只证明协议与编排；真实 token 权限、TLS/网关、目标集成分支、真实 review 文本与人工合并需要用户按 §7 执行。
- P5 **没有**修改产品代码以外的验收产物：5b 只新增 E2E 脚本、README P5 章节、本 findings 与 P5 plan 状态；src/test/client/package.json 未改。
- 后续最值得优先做的是 P6 的平台写回、Review 修复轮 lint/test、closed MR 与 notes 分页；它们都是当前行为可解释但用户可感知的缺口。
