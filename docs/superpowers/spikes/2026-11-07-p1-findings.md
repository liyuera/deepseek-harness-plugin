## 3. review 轮次上限 — `P1-E2E-2`

同一套动作先把 `P1-E2E-2` 推到 `mr_open`（`mr.iid=102`，`rounds=0`），再连续触发 review 变更。

| # | action | POST | workflow | rounds | blockedFrom | blockedReason | 响应 code |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1–8 | create → … → `mr_created` | 200 | `mr_open` | 0 | - | - | - |
| 9 | `review_requests_changes` | 200 | `fixing_review` | 1 | - | - | - |
| 10 | `review_fix_done` | 200 | `mr_open` | 1 | - | - | - |
| 11 | `review_requests_changes` | 200 | `fixing_review` | 2 | - | - | - |
| 12 | `review_fix_done` | 200 | `mr_open` | 2 | - | - | - |
| 13 | `review_requests_changes` | 200 | `fixing_review` | 3 | - | - | - |
| 14 | `review_fix_done` | 200 | `mr_open` | 3 | - | - | - |
| 15 | `review_requests_changes`（第 4 次） | **409** | `blocked` | 3 | `mr_open` | `review-rounds-exhausted` | `review-rounds-exhausted` |
| 16 | `retry` | 200 | `mr_open` | 3 | `null` | `null` | - |

第 15 步响应体（节选）：

```json
{"ok":false,"code":"review-rounds-exhausted","message":"Review 已进行 3 轮，达到上限 3 轮，需人工介入","ticket":{"code":"P1-E2E-2","workflow":"blocked","blockedFrom":"mr_open","blockedReason":"review-rounds-exhausted","mr":{"iid":102,"state":"open","verdict":"changes","blockingIssues":[{"id":"R3","severity":"blocking","body":"第 3 轮阻塞问题"}],"rounds":3}}}
```

验证点：

- 第 4 次 review 请求**没有**增加 `rounds`、没有把 R4 写入 `blockingIssues`（拒绝发生在效果应用之前），响应 `ticket` 是被 block 后的完整工单。
- 时间线新增 `blocked` 事件，`actor=system`，message `工单已阻塞：review-rounds-exhausted`。
- `retry` 清除 `blockedFrom`/`blockedReason`，回到 `mr_open`，保留 `rounds=3`、`mr` 上下文和上一轮阻塞项。
- 第 4 次请求使用的 `actionId` 与 block 派生键为 `${actionId}:review-rounds-exhausted`（宿主内部），重复提交同一 actionId 会重放已阻塞结果而不是追加第二次 blocked 事件（由 routes 单测覆盖；本轮未额外制造重复请求）。

| # | 请求 | 结果 |

## 10. 与 spec 的偏差 / 对 P2 的交接

1. **工单是 profile 全局的**：spec 的「按工作区」只落实在 settings（cwd 为 key）；`tickets` 没有 workspace 字段。P2 同步真实工单前必须决定：是否按 workspace 隔离、同一工单多 workspace 时如何合并、启动时如何迁移 P1 存量票。
2. **假引擎是 P1 的范围收窄**：spec P1 验收写的是「假子代理 / 假 MR」，实现进一步简化为**看板按钮手工 POST 假 payload**，没有子代理/worktree/GitLab 进程。P3–P5 需要把动作来源从「用户点按钮」换成 adapter，状态机与持久化不动。
3. **`workspace.configured` 语义**：目前只表示 session 解析到目录，不表示「已保存绑定」。看板用它来禁用写操作；P2 若要求「未配置 GitLab 项目就不允许进入修复/MR」，需要新增显式绑定状态与 host 端校验。
4. **未接 locale**：文案全部硬编码中文；spec §10 要求 `ctx.locale`，package.json 已导出 `./locale/*.json` 但目录/文件尚未创建。
5. **实时推送**：spec §10 提到 SSE `/bug-board/events`；P1 用 3 s 轮询 `snapshot`。P2 工单量大时再评估 SSE 或增量接口。
6. **tab 标题**：spec 写「标题 = 项目名」；P1 固定「Bug 看板」。P2 绑定工作区后再按项目名动态生成。
7. **入口兜底**：P0 已证实右栏第三方占座可行，故未实现会话标题栏按钮 + `shell.overlay` 抽屉；若未来宿主变更导致占座失效，再启用兜底。
8. **review 轮次语义**：`review_fix_done` 后 `mr.verdict` 仍是 `changes`，直到下一次 `review_pass` 才变 `pass`；第 4 次被拒时保留上一轮 `blockingIssues`（R3），不记录 R4。看板/时间线目前能区分（workflow=`fixing_review`/`mr_open`、message 带轮次），P5 若要展示「每轮 review 历史」需新增结构，不能只靠单一 `verdict`。
9. **路由命名空间**：P1 实际为 `/bug-workflow/api/*`（spec 示例为 `/bug-board/api/*`），P2 适配器/文档沿用 P1 路径。
10. **安全**：Origin 比较不区分 http/https（只比 host:port），本机直连无影响；若 P2 前加反向代理改写 Host，需引入可信代理配置，否则浏览器请求会被 403。settings POST 无 actionId（整表 upsert 天然幂等）；action 幂等账本只记成功结果，最多 500 条。
