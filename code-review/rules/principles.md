# AI 生成代码的审查原则

这些原则用于硬规则覆盖不到的长尾问题，也是拿不准时的取舍依据。硬规则给出可核对的条件，原则给出判断方式。

## 审查方式

- 只看 diff：问题必须落在本次新增或修改的行上。旧代码的既有问题，除非被本次改动触发或放大，否则不报。
- 拿不准不报：只报能从 diff 或只读上下文确认的问题。不用「可能」「建议考虑」占位，不把猜测写成结论。
- 按严重度排序：先报必然出错、可被利用或会破坏数据的问题；再报健壮性与成本；纯风格只到 nit。
- 同根因只报一次：同一缺陷出现在多个调用点时合并为一条，location 取最典型的一处。
- 引用规则 id：命中硬规则时用对应 id；硬规则未覆盖但确有把握的长尾问题用 `PRINCIPLE-<dimension>`。
- 给可执行修复：每条 finding 同时说明问题与具体改法，不写泛泛的设计口号。

## 证据与治理边界

- 证据边界：问题必须能由本次 diff 或你亲自用只读工具核实过的文件内容直接证明；不要仅凭 diff 缺失就断言变量未定义、导入缺失、环境变量未声明或某逻辑不存在。
- 团队规范优先：硬规则/团队口径优先于通用最佳实践；冲突时按团队规范执行。
- 风格豁免：纯命名/格式/风格问题只有命中硬规则时才报，否则不报。
- 不重复治理：项目基础层已统一封装的职责（请求、错误提示、权限、日志）不得要求在调用点重复实现；本 diff 未改封装层时，不因调用点没有单独 try/catch 或弹框而报问题。
- 最小修复：suggestion 给出改哪行/怎么改的最小可执行方向，不提大规模重构、重命名或架构调整。
- 数量与排序：最多 20 条，按严重度降序；没有真实问题返回空数组，不为凑数报风格偏好。

## 判断边界

### 正确性

问：改动在真实输入下是否做对了该做的事。

阻塞：结果错误、崩溃、静默失败、数据不一致，或留下难以恢复的副作用。

放过：等价写法、可读性偏好、与本次改动无关的既有问题。

### 安全性

问：是否引入新的信任边界或信息暴露。

阻塞：凭据、令牌或个人数据外泄，越权访问，注入，路径穿越，关闭传输校验。

放过：不接触敏感数据的纯内部调试信息（仍建议清理）。

### 性能

问：是否引入随数据量放大的成本。

阻塞：成本随条目数线性放大的 I/O 或查询、无上限的全量扫描、阻塞主线程的大计算。

放过：常数级小开销、已被上层缓存的重复计算、只在启动时执行一次的成本。

### 可维护性

问：下一个改这段代码的人是否会被误导。

阻塞：注释与代码矛盾、同一事实的两份真相、无法独立测试的多职责函数。

放过：命名偏好、目录位置、注释多少。

## 行为与生命周期

- 用户触发的每个操作都必须有终态出口：成功、无结果、失败至少一种可见反馈；静默 return 视为缺陷。
- 有副作用的挂载必须成对撤销：监听、订阅、定时器、视图约束、层级限制；写入前保存原值，卸载时还原。
- 异步结果回写前校验请求代次，过期结果不得覆盖当前状态。
- 挂载/卸载、激活/停用之间对同一状态的口径必须一致，注释与代码不得互相矛盾。
